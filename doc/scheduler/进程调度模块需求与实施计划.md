## 4. 当前调度基线

当前 `TaskManager` 使用单个 `VecDeque` 保存就绪任务：

- 新任务或被挂起的任务从队尾加入。
- 调度器从队首取出下一个任务。
- 用户态时钟中断到来后，当前任务被挂起并重新加入队尾。
- 定时器频率为 100 Hz，一个 tick 约为 10 ms。

因此，当前实现是一个简单的、时间片约为 1 tick 的 Round-Robin 调度器。

正式修改前必须运行并记录该基线，供重构回归和最终对比使用。

## 5. 已确认的调度方案

主调度算法确定为：优先级调度加老化。

同时保留 Round-Robin 调度器，作为可插拔框架的另一个实现以及最终对比基线。

### 5.1 优先级规则

- 优先级范围：`0..=7`。
- 数值越大，优先级越高。
- 新进程默认基础优先级为 `4`。
- `fork` 创建的子进程继承父进程的基础优先级。
- `exec` 不改变进程的基础优先级。
- 调度器优先选择有效优先级最高的就绪任务。
- 相同有效优先级的任务采用 Round-Robin。

### 5.2 时间片与抢占规则

- 固定时间片暂定为 `2 ticks`，即约 20 ms。
- 当前任务用完时间片后被抢占并重新加入就绪队列。
- 如果就绪队列中出现优先级更高的任务，当前低优先级任务最迟在下一次时钟中断时被抢占。
- 如果时间片尚未耗尽且没有更高优先级任务就绪，则当前任务继续运行，避免无意义的上下文切换。

### 5.3 老化规则

老化用于防止低优先级任务永久得不到 CPU。

- 只有处于 `Ready` 状态的任务参与老化。
- 睡眠、阻塞和退出状态不累计老化等待时间。
- 任务每等待 `20 ticks`，有效优先级提高一级。
- 有效优先级最高不超过 `7`。
- 任务获得 CPU 后，本次等待产生的老化提升清零。
- 清除老化提升不会修改用户设置的基础优先级。

有效优先级计算规则：

```text
effective_priority = min(
    7,
    base_priority + ready_wait_ticks / 20
)
```

## 6. 可插拔调度框架

建议定义统一的调度器接口：

```rust
pub trait Scheduler {
    fn enqueue(&mut self, task: Arc<TaskControlBlock>);
    fn dequeue(&mut self) -> Option<Arc<TaskControlBlock>>;
    fn should_preempt(&mut self, current: &Arc<TaskControlBlock>) -> bool;
}
```

提供两个实现：

```text
RoundRobinScheduler
PriorityScheduler
```

通过内核配置常量选择调度策略，例如：

```rust
pub const SCHEDULER_POLICY: SchedulerPolicy =
    SchedulerPolicy::PriorityAging;
```

最终应能够通过修改调度策略配置并重新编译，在不改动任务切换主流程的情况下切换调度算法。

## 7. 优先级调度器内部结构

优先级调度器使用 8 个 FIFO 就绪队列：

```rust
pub struct PriorityScheduler {
    ready_queues: [VecDeque<Arc<TaskControlBlock>>; 8],
}
```

队列含义：

```text
ready_queues[7]  最高优先级
ready_queues[6]
...
ready_queues[1]
ready_queues[0]  最低优先级
```

任务进入就绪状态时：

1. 记录本次进入就绪队列的时间。
2. 清零当前时间片计数。
3. 根据当前有效优先级进入对应队列。

调度器选择任务时：

1. 检查就绪任务是否达到老化条件。
2. 将需要提升的任务移动到更高优先级队列。
3. 从优先级 7 向优先级 0 查找第一个非空队列。
4. 从该队列队首取出任务。
5. 累计任务的就绪等待时间。
6. 增加任务的被调度次数。
7. 清零时间片计数和本次老化提升。

任务时间片耗尽后，如果仍为就绪状态，则回到相应队列的队尾。

## 8. 调度信息数据结构

建议在 `TaskControlBlockInner` 中增加：

```rust
pub struct SchedInfo {
    /// 用户设置的基础优先级。
    pub base_priority: usize,

    /// 基础优先级加上老化产生的临时提升。
    pub effective_priority: usize,

    /// 本次进入就绪队列的调度 tick。
    pub ready_since: usize,

    /// 累计实际运行 tick。
    pub runtime_ticks: usize,

    /// 累计处于 Ready 状态的等待 tick。
    pub total_wait_ticks: usize,

    /// 累计被调度运行的次数。
    pub scheduled_count: usize,

    /// 当前时间片已经使用的 tick 数。
    pub slice_ticks: usize,
}
```

字段更新时机：

| 事件 | 更新内容 |
|---|---|
| 创建进程 | 基础优先级和有效优先级初始化为 4 |
| `fork` | 子进程继承父进程基础优先级 |
| 进入就绪队列 | 记录 `ready_since` |
| 等待过程中 | 根据等待时间计算有效优先级 |
| 被选中运行 | 累计等待时间，调度次数加一，时间片清零 |
| 用户态时钟中断 | 运行时间和已用时间片各加一 |
| 时间片耗尽 | 状态改回 Ready 并重新入队 |
| 阻塞或退出 | 不再累计就绪等待时间 |

## 9. 系统调用接口

### 9.1 系统调用编号

```rust
const SYSCALL_SET_PRIORITY: usize = 1040;
const SYSCALL_GET_PRIORITY: usize = 1041;
const SYSCALL_GET_SCHED_STATS: usize = 1042;
```

### 9.2 设置优先级

```rust
set_priority(pid, priority) -> isize
```

规则：

- `pid == 0` 表示当前进程。
- 其他 PID 表示指定进程。
- 修改基础优先级。
- 如果进程正在就绪队列中，需要使其任务进入正确的优先级队列。
- 多线程进程的所有存活线程使用相同基础优先级。

返回值：

```text
 0  设置成功
-1  PID 不存在
-2  优先级不在 0..=7 范围内
```

### 9.3 查询优先级

```rust
get_priority(pid) -> isize
```

规则：

- `pid == 0` 表示当前进程。
- 返回基础优先级，不返回老化后的有效优先级。

返回值：

```text
0..=7  查询成功
-1     PID 不存在
```

### 9.4 查询调度统计

用户态接口：

```rust
get_sched_stats(pid, &mut stats) -> isize
```

用户态和内核态使用布局一致的结构：

```rust
#[repr(C)]
pub struct SchedStats {
    pub pid: usize,
    pub base_priority: usize,
    pub effective_priority: usize,
    pub runtime_ticks: usize,
    pub total_wait_ticks: usize,
    pub scheduled_count: usize,
}
```

返回值：

```text
 0  查询成功
-1  PID 不存在
-2  用户输出地址无效
```

多线程进程的统计规则：

- `runtime_ticks` 为所有存活线程统计值之和。
- `total_wait_ticks` 为所有存活线程统计值之和。
- `scheduled_count` 为所有存活线程统计值之和。
- `effective_priority` 取所有存活线程中的最高值。

## 11. 测试文件与验收标准

测试源文件放在 `user/src/bin/`，必须提交 Git，不加入 `.gitignore`。

### 11.1 基线测试

修改调度器前运行并记录：

- 系统编译和启动结果。
- Shell 运行结果。
- `yield`、`sleep_simple`、`forktest_simple`、`threads` 和 `usertests` 结果。
- 多个任务是否能轮流运行。
- 不调用 `yield` 的任务是否会被时钟中断抢占。

### 11.2 优先级调度测试

文件：`user/src/bin/scheduler_priority.rs`

- 创建高、中、低三个优先级进程。
- 同时执行 CPU 密集型工作负载。
- 高优先级进程应更早完成或获得明显更多的 CPU 时间。

### 11.3 抢占测试

文件：`user/src/bin/scheduler_preempt.rs`

- 创建至少两个不主动调用 `yield` 的 CPU 密集型进程。
- 两个进程都必须获得 CPU。
- 两个进程的 `scheduled_count` 都应大于 1。

### 11.4 同优先级公平性测试

文件：`user/src/bin/scheduler_fairness.rs`

- 创建多个相同优先级进程。
- 每个进程都必须获得运行机会。
- 最大运行时间与最小运行时间的差异目标不超过约 20%。

### 11.5 老化与防饥饿测试

文件：`user/src/bin/scheduler_aging.rs`

- 同时运行持续占用 CPU 的高优先级进程和最低优先级进程。
- 低优先级进程的有效优先级应随等待时间提高。
- 低优先级进程必须最终被调度。
- 目标是在不超过 200 ticks 的时间内获得运行机会。

### 11.6 调度统计测试

文件：`user/src/bin/scheduler_stats.rs`

- `runtime_ticks` 应在实际运行后增加。
- `total_wait_ticks` 应在就绪等待后增加。
- `scheduled_count` 应在任务被选中时增加。
- 各累计统计值不能倒退。
- 阻塞时间不能错误计入就绪等待时间。

### 11.7 系统调用异常测试

文件：`user/src/bin/scheduler_syscall.rs`

- 合法设置返回 0。
- 超出范围的优先级返回 -2。
- 不存在的 PID 返回 -1。
- 错误调用不得导致内核 panic。

### 11.8 最终回归与对比

对相同工作负载分别使用 `RoundRobinScheduler` 和 `PriorityScheduler`，对比：

- 任务完成顺序。
- 运行时间。
- 等待时间。
- 被调度次数。
- 高优先级任务的响应效果。
- 低优先级任务是否发生饥饿。

最后重新运行原有的进程、线程、睡眠和同步测试，确保调度重构没有破坏已有功能。

## 19. Round-Robin 对比结果

对同一个 700 ms 高/低优先级 CPU 工作负载分别编译两种调度策略，实测结果：

| 调度策略 | 高优先级运行时间 | 低优先级运行时间 | 差值 | 结论 |
|---|---:|---:|---:|---|
| Priority-Aging | 62 ticks | 0 ticks | 62 | 短时间内优先保障高优先级任务 |
| Round-Robin | 30 ticks | 32 ticks | -2 | 不区分优先级，CPU 时间基本均分 |

该对比证明两种调度器确实通过统一框架执行了不同策略，而不是仅保存了未使用的实现代码。
